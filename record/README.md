# AI 協作紀錄：候診清單（AI-Patient-Triage-System）


## 1. 專案與協作方式

- **目標**：在「病人輸入症狀 → AI 評估 → 醫師查看」的基礎上，讓醫師開頁就看到整個候診隊伍，並能看出誰最需要優先處理。
- **工具**：Claude（討論方向、產出規格與程式、跑測試）；Vue 3、Express 5、Gemini、HAPI FHIR（https://hapi.fhir.org/baseR4）、Postman、瀏覽器。
- **分工**：AI 提出方案、列出取捨、寫程式與測試；我負責提出需求、選擇方案、在自己的電腦實際執行並用截圖驗證。
- **方法**：先只討論大方向與順序（不寫程式）→ 把決定寫成規格（JSON）→ 分 5 個小步驟實作 → 每一步先看「要驗證什麼」的檢查清單，再逐項實測，通過才進下一步。
- **核心主張**（討論後形成）：AI 負責排優先順序，醫師負責決定，系統留下可追溯的紀錄。

## 2. 協作過程：想法與決定

每一項都分開寫：我提供了什麼、AI 回應了什麼、我怎麼決定。

### 2-0 起點：決定做什麼
- **我提供**：系統基礎是「病人輸入自己的症狀，系統產生評估結果，醫師可以查看」；要求先只討論大方向、功能、實作順序，不要寫程式。
- **AI 回應**：讀過專案（design 文件與程式）後，指出現況的缺口：醫師只能輸入病人 ID 才看得到、AI 只看單一句話、沒有規則保底、醫師處置沒有紀錄；並提出三層功能清單與實作順序。
- **我的決定**：以「候診清單」作為第一個延伸。我寫的三句架構（需求：醫師要查看評估結果；功能：取得評估結果的 API 並顯示；實作：Express API、FHIR 查詢、Vue 畫面）被對應到清單中的第 2 步。
- **理由**：先打好基礎，日後再向上延伸/增加。

### 2-1 API 怎麼設計
- **我提出**：「API 用參數的方式處理，盡量簡化函式處理。」
- **AI 回應**：翻成「一支 API、條件放 query 參數」，參數大多能直接對應 FHIR 搜尋參數；後端函式只剩檢查參數、查 FHIR、攤平資料。
- **我的決定**：採用。
- **理由**：函式少、CDS 之後可共用同一套查詢；方便維護

### 2-2 同一位病人要列幾筆
- **AI 提供選項**：A 全部紀錄都列（簡單，但同一人會出現多列）；B 每人只留最新一筆（符合候診情境，後端要多整理一步）。
- **我的決定**：B。
- **AI 補充的風險**：看我的測試資料，同一位病人 13:44 被評 9 分、14:35 又送一筆被評 2 分；只留最新一筆會把 9 分藏起來。
- **理由**：醫生在有限的時間內，針對病人最新身體狀態去診斷。

### 2-3 怎麼避免高分被最新一筆蓋掉
- **AI 提供選項**：加「近期最高分」欄位／維持原案並說明限制／改成每人留最高分那筆。AI 傾向第一種。
- **我的決定**：每位病人多回傳「近期最高分」。
- **後續**：實測時，我讓同一位病人先送高風險、再送一句含蓄的話，AI 只給 3 分；清單同時顯示「急迫 3」與「⚠ 近期最高 10」，這個欄位確實避免了漏看。
- **理由**：醫生在有限的時間內，針對病人最新身體狀態去診斷。另對"警示病患者"須特別注意。

### 2-4 排序規則
- **AI 提出取捨**：`sort=score` 目前是「最新一筆需人工介入者在前 → 近期最高分 → 時間」。問題是「最新 2 分但近期 10 分」的病人會排在「3 分但需人工」的後面。
- **我的決定**：維持現狀。
- **AI 的理由**：需人工介入是 AI 明確的訊號，優先級最高；近期最高分的病人仍有提示標籤。
- **理由**：醫生在有限的時間內，針對病人最新身體狀態去診斷。另對"警示病患者"須特別提醒。

### 2-5 醫師頁怎麼擴充
- **AI 提議**：清單加明細：上方是候診清單，點一位病人，下方載入原有的病歷與 CDS 卡片，不用二選一。
- **我的決定**：同意。
- **理由**：保留第一階段完整流程，簡報能展示「清單 → 點進去 → AI 建議 → 轉介」；可直覺性操作介面。

### 2-6 CDS 卡片：最新低分但近期有高分時怎麼辦
- **發現**：實測時清單提示「近期最高 10」，點進去卡片卻寫「AI 暫無高優先提示」，兩邊說法不一致，原因是 CDS 只讀最新一筆。
- **AI 提供選項**：A 只加一行提示；B 升級成警示卡並附轉介按鈕。AI 建議 B。
- **我的決定**：B。
- **理由**：現在或曾經是"警示病患者"皆須特別提醒。

### 2-7 錯誤訊息
- **我提出**：把「Failed to fetch」改成「無法連線到後端伺服器」。
- **我的決定**：已採用並驗證。


## 3. 逐步實作與驗證

| 步驟 | 我要求／AI 產出 | 我怎麼驗證 | 結果 |
|---|---|---|---|
| 1 後端查詢 | 依參數查 FHIR，新舊代碼一起查，查不到回 200 空陣列 | 瀏覽器打網址：不加參數、`patientId`、不存在的病人、`limit` | 通過 |
| 2 整理與排序 | 每人只留最新一筆、近期最高分、`minScore`、`sort`、`truncated` | 8 項網址測試＋從病人端送新資料，確認新病人與最新一筆立即更新 | 通過（需補測試資料） |
| 3 錯誤處理 | 參數錯誤回 400；FHIR 失敗回錯誤而非空陣列 | 7 種不合法參數；故意改錯 FHIR 位址 | 通過 |
| 4 醫師頁 | 候診清單、四種狀態、點選病人載入明細 | 自動載入、點四位病人、重新整理、窄視窗、關後端 | 通過（樣式失效後修正） |
| 5 CDS 共用 | 與清單共用查詢，新增「近期曾有高分」卡 | 新卡片內容、建立 Task 後到 FHIR 查看內容、其他病人卡片與以前一致、清單 API 輸出 | 通過 |

每一步都有畫面截圖可作為證據（可附在報告後面）。

## 4. AI 出錯、我的疏漏，以及怎麼處理

這一節是我認為最能顯示「我有檢查 AI」的部分。

1. **樣式沒生效**：AI 把新樣式放在 `</style>` 後面，清單變成純文字。AI 自己的測試沒有檢查到，是我看畫面截圖發現的。AI 承認漏檢，修正後我重新驗證。
2. **預測不完整**：AI 給的預期結果表漏了 patient-tw-001，導致我的實測和預期「看起來不同」。我實測後確認程式行為是對的，是預期表不完整。
3. **時間字串**：AI 的測試發現 Node 在日期與時間之間放了特殊空白字元；AI 改成自己組字串，避免不同環境輸出不同。
4. **測試資料不足**：一開始只有一位病人，第 2 步（每人一筆）無法驗證。AI 提醒後，我補了其他病人的資料。
5. **我的操作問題**：用 Postman 的 POST 建立病人，FHIR 自己換了 ID，病人端仍然寫入失敗；改用 PUT 並把 ID 寫在網址才成功。我學到：POST 是新增、ID 由伺服器決定；PUT 才能指定 ID。
6. **FHIR 參考完整性**：Observation 引用的病人必須先存在，否則 FHIR 回 400（HAPI-1094）。我學到寫入前要確認被引用的資源存在。
7. **AI 評分的限制**：同一位病人先前有高風險紀錄，後來一句含蓄的話只被評 3 分。這不是程式錯誤，而是 AI 每次只看單一句話的限制，因此才有「近期最高分」的設計。


## 5. 未來可優化程式的方向

- 沒有「已處置」狀態，醫師處理過的病人不會離開清單（例如三週前的紀錄仍在最上面）。
- AI 每次只看單一句話，含蓄語句可能被低估；可考慮把近期紀錄交給 AI，或加關鍵字規則。
- 病人端不能建立新病人，病人要先存在於 FHIR。
- 其他延伸：追問式問診、分數趨勢、SMART on FHIR。
